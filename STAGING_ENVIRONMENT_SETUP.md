## Database baseline and migration order

The repository currently has **no fresh-database baseline migration** for the application's core schema. The tracked SQL files are incremental changes and assume the underlying schema already exists. In particular, there is no tracked migration that creates the core `profiles`, `notifications`, `follows`, `stories`, `community_groups`, `community_group_members`, direct-message tables, or `push_subscriptions`. Do not treat the list below as sufficient to bootstrap an empty Supabase project.

### Required core schema (not present in tracked migrations)

A database owner must define and review a clean baseline for at least:

- **Authentication/profile:** Supabase Auth integration and `public.profiles` linked to `auth.users`; columns used in the client and Edge Function include profile ID, username, display name, avatar URL, introduction, admin status, and timestamps. The app creates or repairs the signed-in user's profile client-side, so the baseline needs safe own-row insert/update/select RLS. Admin status must not be self-assignable.
- **Social/content:** `follows`, `blocks`, `posts`, `post_likes`, `comments`, `comment_likes`, `stories`, `notifications`, and `reports`, including IDs, authors/recipients, references, notification type/read fields, timestamps, and constraints referenced by app code and migration files. Establish notification recipient/actor and relationship columns, including `message_id`, `group_message_id`, `post_id`, `comment_id`, `group_id`; later migrations add join-request/story IDs.
- **Messaging:** `conversations`, `conversation_members`, `messages`, `message_reads`, and `message_deletions`, with the unique constraints relied on by upserts and direct-chat RPCs. The blocking migration requires `private.is_messaging_allowed` and `private.user_conversation_ids` helpers plus a `blocks` relation.
- **Groups:** `community_groups`, `community_group_members` (including `role`), `community_group_messages`, `community_group_message_reads`, and group report support; include admin helper/RPC dependencies before the group-hardening migration.
- **Push:** `push_subscriptions` with `id`, `user_id`, unique endpoint, serialized subscription and optional user-agent/timestamps. RLS must scope management to the signed-in owner. The Edge Function uses the service role only server-side.

This list is a dependency inventory, **not a complete schema definition**. Reconstructing the full baseline safely is **not currently possible from this repository alone**: the original core schema, its complete RLS policy definitions, constraints, storage limits/MIME rules, and all helper functions are not tracked here. Do not invent these from TypeScript usage or copy production data/schema blindly. A responsible database owner must recover/author a reviewed schema-only baseline, test it on a disposable isolated database, and verify all client access paths and constraints. No seed data should be copied from production.

### Seed data, Auth, Storage, Realtime, and Edge Functions

- **Seed data:** no production rows. Create synthetic staging accounts through the staging Auth UI/API and synthetic posts/groups/messages only. Ensure the first moderator/admin is provisioned through a reviewed server-side process; never grant `is_admin` through client-updatable profile fields. Do not seed real users, tokens, subscriptions, or content.
- **Auth configuration:** in staging **Authentication → URL Configuration**, set the staging app/Preview URLs and exact redirect allow-list entries for login, email confirmation, and password recovery. Review signup/email confirmation and provider settings before testing. The app calls a `username-auth` Edge Function for username sign-up/login, but that function's source is not tracked here; obtain and review that dependency before claiming the auth journey is deployable. Use staging-only accounts and test email delivery behavior; do not copy production provider secrets or user identities.
- **Storage:** the app expects buckets `banjara-profile-avatars`, `banjara-media`, `banjara-chat-media`, `banjara-group-media`, and `banjara-stories`. Define per-bucket size/MIME limits and owner/member-aware policies in the baseline. Profile avatars use public URLs; post/chat/group assets use signed URLs; story media is expected private and its migration tightens the stories bucket policy. The story privacy migration assumes the bucket and related tables already exist.
- **Realtime:** enable the Supabase Realtime publication for the tables subscribed to by the app, at minimum `public.messages` for direct-chat updates. The private activity-status migration requires `supabase_realtime` to exist and adds `public.user_privacy_settings`. Review all app subscriptions against the baseline publication; do not assume all tables should be published.
- **Edge Functions:** only `send-chat-push` is present under `supabase/functions` in this repository. The frontend also invokes `username-auth`, `ai-moderator`, and `banjara-ai`; their function sources are absent here and must be obtained/reviewed or those features disabled for staging. The moderation migration adds a reviews table but does not provide the worker. Incoming-call push is not implemented.

After the reviewed baseline exists, apply the tracked incremental migrations in the order below. Verify each migration's migration-history state first. Keep the baseline schema-only and confirm its history handling before `db push`.

Then apply the tracked migrations in this exact timestamp order (Supabase CLI normally orders versions lexically):

1. `20261006124631_optimize_rls_auth_uid_and_remove_duplicate_notification_index.sql` — assumes existing RLS policies and notification index.
2. `20261006124750_enforce_blocking_in_direct_messaging_rls.sql` — assumes `private.is_messaging_allowed`, blocks, conversations, members, messages, and message-read tables.
3. `20261006124903_make_story_media_private_and_signed.sql` — assumes the `banjara-stories` storage bucket, stories, and blocks.
4. `20261006142000_add_missing_foreign_key_indexes.sql` — indexes existing tables including profiles, notifications, posts/comments, messages, groups, and reports.
5. `20261006150000_bound_community_group_reports.sql` — assumes reports and group-admin helper functions.
6. `20261006153000_race_safe_direct_conversation_creation.sql` — assumes blocks and direct-conversation tables/constraints.
7. `20261006170000_harden_group_rpcs_and_realtime_races.sql` — assumes groups, group members/messages, reports, and group-admin helpers.
8. `20261006210000_add_community_group_join_requests.sql` — creates join requests and `notifications.group_join_request_id`; assumes profiles, notifications, groups, and members.
9. `20261006211000_add_group_message_selection_deletes.sql` — assumes group messages, group members, and profiles.
10. `20261008184500_add_story_viewers.sql` — creates `story_views`; assumes stories and profiles.
11. `20261027110000_add_ai_moderation_reviews.sql` — creates moderation reviews; assumes reports and profiles with `is_admin`.
12. `20261027120000_add_activity_status_privacy.sql` — superseded/no-op marker; it contains comments only and makes no schema change.
13. `20261102100000_move_activity_status_to_private_settings.sql` — creates private settings and migrates an optional profile column; must follow the activity-status setup above.
14. `20261102110000_add_push_delivery_idempotency_and_follow_notifications.sql` — assumes `push_subscriptions(id)`, notifications, stories, follows, community memberships and join requests. Also verify the baseline has no duplicate follow/member notification triggers before applying it.
15. `20261103100000_allow_conversation_read_receipts.sql` — allows authenticated members of a direct conversation to read receipt rows for its messages; assumes the direct-message schema and `private.is_messaging_allowed` from migration 2.
16. `20261103110000_add_chat_message_features.sql` — adds same-conversation reply references, edited-message RPCs, member-scoped reactions, per-user pins, protected typing-status tables and realtime publication entries, and member-visible group read receipts. It assumes both message schemas, existing `is_deleted_for_everyone` columns, `community_group_message_reads`, `profiles`, `community_group_members`, and `private.is_messaging_allowed`; review all functions, constraints, existing policies, and publication state against the approved baseline and staging schema before deployment.
17. `20261110110000_add_post_share_counts.sql` — adds per-recipient-chat post share records and a count RPC. It assumes `posts`, `auth.users`, and the existing post visibility policies; verify the insert/select policies on the staging schema before applying it. Until this migration is applied, the homepage displays likes and comments normally and marks share counts unavailable rather than showing a misleading zero.

The chat feature migration is a local draft only. It has not been run against the live database or a staging database. The application preserves the existing message select shape so normal history loading/sending does not require the new columns; using new chat features requires the migration to be applied first. Group reply references are added to newly sent rows, while a persisted reply preview for previously loaded messages still requires loading the feature metadata after schema deployment.

The push migration creates a server-only `push_delivery_events` table and adds `notifications.story_id`; it installs follow/member triggers and updates the join-response RPC. Its foreign keys and trigger functions must be checked against the approved baseline before deployment. `push_subscriptions` ownership RLS also needs explicit review: clients may manage only their own rows; only trusted server code can send.

## Environment templates

- [frontend.staging.env.example](./frontend.staging.env.example) contains only public frontend values. Copy it to `.env.staging` locally (ignored by Git) for Vite's `--mode staging`, or configure the same values in Vercel's **Preview** environment.
- [supabase/secrets.staging.env.example](./supabase/secrets.staging.env.example) contains placeholders for the Edge Function VAPID secrets. Replace placeholders only in a local ignored secrets file, such as `supabase/.env.staging.local`, and never load that file through Vite. Add the real values to Supabase staging secrets using the CLI command below; do not commit them.
- `VITE_VAPID_PUBLIC_KEY` is a public key and must match `VAPID_PUBLIC_KEY` on the staging function. Frontend `VITE_*` values are included in the browser bundle; never place a private key, service-role key, or database password in one.
- Supabase provides `SUPABASE_URL`, `SUPABASE_ANON_KEY`, and `SUPABASE_SERVICE_ROLE_KEY` to Edge Functions. Do not set or copy the service-role key into frontend or Vercel Preview variables.

## Safe commands to use only after project verification

Run commands from the repository root in PowerShell. Substitute the verified staging reference only. The commands below are documentation; none were run for this task.

```powershell
# Authenticate once if required; do not paste tokens into source files.
supabase login

# Link to the verified staging project; enter its database password at the prompt.
supabase link --project-ref <STAGING_PROJECT_REF>

# Inspect history before changing the database.
supabase migration list --linked

# Confirm pending migrations and review the exact pending set before proceeding.
supabase db push --linked --dry-run

# Only after the baseline and every pending migration have been reviewed:
supabase db push --linked

# Put only VAPID_PUBLIC_KEY, VAPID_PRIVATE_KEY, and VAPID_SUBJECT
# in supabase/.env.staging.local, then configure the staging project:
supabase secrets set --project-ref <STAGING_PROJECT_REF> --env-file supabase/.env.staging.local

# Deploy the function only to the same verified staging project:
supabase functions deploy send-chat-push --project-ref <STAGING_PROJECT_REF>
```

If the CLI reports the baseline or earlier versions as pending, **stop**. Do not apply a random subset, use `--include-all`, repair migration history to make the output look clean, or run SQL against an unverified target. Have the database owner reconcile the approved baseline and migration history first. After deployment, check `supabase migration list --linked` again and verify the function's project reference.

1. In Vercel, open the Connect project → **Settings → Environment Variables**. Add `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY` (or `VITE_SUPABASE_PUBLISHABLE_KEY`), and `VITE_VAPID_PUBLIC_KEY` scoped to **Preview only**. Never edit Production-scoped values.
2. Create/push a non-production branch only after the user separately authorizes publishing changes. Let the linked Vercel Git integration create a Preview, or run `vercel` from that branch after verifying the linked Vercel project. Do not run `vercel --prod` or promote the Preview.
3. Verify the Preview's Supabase URL/project ref and the Edge Function's ref are identical. Confirm the VAPID public key matches the staging secret.

The interactive CLI alternative (run once per variable; enter the staging value only when prompted) is:

```powershell
vercel env add VITE_SUPABASE_URL preview
vercel env add VITE_SUPABASE_ANON_KEY preview
vercel env add VITE_VAPID_PUBLIC_KEY preview

# From the approved non-production branch, after checking the linked Vercel project:
vercel
```

Use `VITE_SUPABASE_PUBLISHABLE_KEY` instead of `VITE_SUPABASE_ANON_KEY` if that is the client key issued for staging. Never use `vercel --prod`.
